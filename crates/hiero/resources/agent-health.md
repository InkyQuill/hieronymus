# Project integration and session health

This is the shared check for bootstrap and hieronymus-doctor. Inspect first; a project binding, an MCP connection and installed skills are separate from loaded hooks. Do not claim setup is complete from generated files alone. Do not create a memory session to test setup.

## Project and installed integration

1. Run `hiero project-context --cwd <actual-project-path> --json`; read the reported project instructions and preserve the agreement, selected direction and languages. Do not create a replacement project or overwrite its binding. A ready project result does not install hooks.
2. Check `hiero version`, `hiero status --json` and `hiero doctor --json`, then call advertised `hieronymus_status` through this agent's actual MCP connection. Keep executable, daemon, generated bundle and loaded host cache observations separate. Do not print credentials or private source/prompt text.
3. Inspect the installation-owned bundle under the actual configured data root and the host's active plugin manifest/cache. For Codex, the plugin manifest must point to its MCP registration, skills directory and `hooks/hooks.codex.json`. Check the effective project/user settings and native trust state: `features.hooks=false`, a disabled plugin or unapproved changed command can prevent loading. Do not dump unrelated settings or grant blanket trust. Installing skill symlinks or a `.hieronymus.json` alone does not load hooks.
4. For automatic bound-session handling, verify that the active Codex hook configuration includes UserPromptSubmit, SessionStart and SessionEnd, using `hieronymus-agent-hook ... --host codex` with the same data root as MCP. Check actual contents as well as versions: an older bundle may lack lifecycle events even when a version label matches. Avoid registering duplicate hooks through both a plugin and project settings. For Claude/zCode, inspect the actual compatible bundle/host override. Other hosts need explicit completion unless independently qualified.
5. If setup/repair is requested, run `hiero plugins sync --json` using the intended installation. It regenerates the local bundle and refreshes an already installed, enabled Codex plugin through the native CLI. Missing hosts are advisory; initial registration still uses the host's native setup. Use `hiero plugins status --json` to inspect executable, daemon, generated and Codex disk-cache versions/content drift. Preserve unrelated project settings. If an older binary still generates missing events, a newer application build is required. Reopen conversations after refresh and review changed commands through the host's exact-command trust flow; never forge acceptance or assume a running conversation reloaded.
6. Validate actual loading from native hook diagnostics on a disposable conversation. Use a synthetic project and disposable Hieronymus root for mutating tests. Close/archive that test conversation through the host, then confirm its real lifecycle outcome. Do not send fabricated SessionEnd to prove native integration. If native execution cannot be exercised, label it unverified and use explicit memory-session completion for task-owned work.

Bootstrap should perform these checks when setting up a project or when the integration is missing/stale; on ordinary work reuse current verified setup evidence. A read-only project agreement remains read-only: do not enable prompt retention merely to obtain lifecycle hooks. Explicit completion is available independently of prompt capture.

## Own the task session

Before starting read/learn/translation work, decide whether the current leading workflow already owns a compatible active memory session. Reuse that session when appropriate; nested skills must not create a second one or complete their caller's session. Sessionless research reads do not need a new session.

When this invocation creates a session for a bounded read/learn task, retain its returned session_id and own completion. After its writes and validation finish, call `hieronymus_session_complete` with that exact ID before reporting the task complete, including when aborting a task that will not continue. Check the response. Failed completion stays explicitly pending with the ID and error, not silently abandoned or retried without a bound. If work is deliberately continuing, hand off the active ID and remaining work instead. Completion records lifecycle, not Dream eligibility: observations can be processed while the session is active and together with other sessions. Completion is not proof Dream finished.

Do not wait for the whole chat to close to complete a finished task. `Stop` is the end of an assistant turn, not the end of a memory task: never register blanket completion on Stop. Codex SessionEnd is a fallback for the one explicitly bound session, not for every session the agent ever created. It is not emitted immediately just because the user switches chats. Consult the current [Codex lifecycle contract](https://developers.openai.com/codex/hooks#sessionend); Claude has [its own shutdown timing and hook budget](https://code.claude.com/docs/en/hooks#sessionend). Plugin-specified timeouts alone may not extend Claude's overall shutdown budget.

## Diagnose earlier open sessions

Use the console's Short-Term Sessions view (or its advertised public read APIs) to inspect actual IDs, project, status and last activity. Correlate with known read/learn task results and the actual host binding; do not assume every active session belongs to this chat or query private manuscript text for diagnosis. Report separately: owned task still running, ended task not explicitly completed, unbound session, missing lifecycle hooks, and pending failed termination. Age alone is not evidence of abandonment.

For an ended task whose session ID is established, use explicit `hieronymus_session_complete`; for a stopped host with an intact matching binding, use documented `recover-session` with confirm_abandoned. Unbind removes that recovery association but does not complete the session. Do not re-enable capture merely to recover an unbound session. Never close live/unknown sessions in bulk or patch task_sessions with SQL. If ownership or whether work ended cannot be established, ask only about those specific sessions.

A SessionEnd acknowledgement lost after server completion is recoverable idempotently; an activity change after the recorded ending must not be overridden. SessionStart/resume cancels a pending termination for an active bound session, not an explicit unbind pause. If memory completion already happened, create a fresh session only for new work and explicitly bind it if capture is intended.

## Local hook trust boundary

Hook stdin and `--host` identify the expected envelope and binding; they do not cryptographically prove the caller is Codex/Claude/zCode. Another process running as the same OS user can invoke these commands, including completion/cancellation. Private files, exact binding identity, activity checks, the conversation lock and authenticated daemon transport protect different boundaries; they do not attest native host provenance.

A token readable by all processes of that user, executable-name checks or parent-PID checks would not create a stronger reliable origin boundary. Current documented hook envelopes provide no independently verifiable signature. Do not add a shared-secret check and claim host attestation. A stronger design needs host-issued, independently verifiable provenance or OS isolation that actually denies unrelated callers access, with explicit replay/resume semantics. Until such a facility is available and qualified, treat hooks as local-user automation and never synthesize trusted events from model text.

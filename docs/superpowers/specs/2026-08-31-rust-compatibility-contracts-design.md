# Rust Compatibility Contracts Design

**Status:** Proposed for review on 2026-08-31.

## Goal

Make “parity” a finite, reviewable inventory rather than a promise to port an
unspecified subset of Python tests.

## Compatibility Manifest

Create a versioned manifest whose entries have:

- stable contract id;
- surface: CLI, MCP, HTTP, WebSocket, config, database, agent integration,
  frontend, install/update, or diagnostics;
- current Python entry point and owning test files;
- canonical request/input fixture;
- canonical success and error outputs with volatile fields normalized;
- Rust test target;
- disposition: preserve, intentionally change with ADR, or remove with ADR.

The initial manifest is generated by inventorying all Click commands, 39 MCP
tools, HTTP/WebSocket routes, config fields, database tables and migrations,
agent-plugin targets, frontend API calls, installer behaviors, and tests. The
manifest must not cite nonexistent test files. Every current test maps to one or
more entries or is marked implementation-internal with a reason.

## Contract Fixtures

Fixtures are immutable JSON, text, TOML, SQLite, and filesystem trees stored
under a dedicated compatibility test directory. Sensitive example values are
synthetic. Fixtures cover:

- human CLI output only where user-facing wording is intentional;
- JSON CLI output and exit codes for automation;
- MCP tool names, descriptions, input schemas, result envelopes, and errors;
- exact HTTP methods, paths, request bodies, response bodies, status codes, and
  authentication requirements;
- WebSocket message types and reconnect behavior;
- config defaults, redaction, load/save round trips, and legacy migration;
- database schema variants and representative domain data;
- generated host configuration and idempotent reinstall/uninstall behavior.

## Differential Harness

The harness can run the Python reference and Rust candidate against independent
copies of the same fixture. It normalizes timestamps, temporary paths, ports,
generated ids, and nondeterministic ordering only where the contract explicitly
allows variation. It never normalizes semantic differences.

For ranking, fixtures assert deterministic lane membership and ordering, plus
documented numeric tolerances for BM25/RRF values. Provider and embedding calls
use deterministic fakes. Native LanceDB contract tests supplement, but do not
replace, fake-index tests.

## Change Control

A mismatch is resolved by fixing Rust, correcting an erroneous fixture against
the Python source, or accepting an ADR-backed contract change. Updating expected
output merely to make a test pass is prohibited.

The manifest records the first Rust release that implements each contract and
the last Python release used as its reference.

## Acceptance Criteria

- Every current Python and frontend test has a manifest disposition.
- Every public CLI command, MCP tool, route, and config field has at least one
  success fixture and one relevant failure fixture.
- The harness detects deliberate changes to method, path, field name, exit
  code, authentication, and deterministic terminology behavior.
- CI publishes a readable parity report listing implemented, changed, removed,
  and outstanding contracts.
